# Stash Config

Git-tracked configuration and curated metadata for the Stash media manager running on this machine.

## What lives here

| Path | Purpose | Tracked in git? |
|---|---|---|
| `config.example.yml` | Redacted config template (secrets stripped) | Yes |
| `config.yml` | Real config with live secrets | **No** (gitignored) |
| `scripts/Backup-StashDatabase.ps1` | Safe DB backup via GraphQL -> compress -> NAS | Yes |
| `scripts/Sync-StashMetadataExport.ps1` | Copy curated metadata, strip cover images | Yes |
| `scripts/Invoke-StashMetadataExport.ps1` | Trigger Stash full JSON export | Yes |
| `scripts/Export-StashSummary.ps1` | Compact stats/tags/studios summary via GraphQL | Yes |
| `exports/scenes/` | Scene JSONs (covers stripped) | Yes |
| `exports/performers.json` | Performers via GraphQL | Yes |
| `exports/studios.json` | Studios via GraphQL | Yes |
| `exports/tags.json` | Tags via GraphQL | Yes |
| `plugins/` | Custom Stash plugins (future) | Yes |
| `stash-go.sqlite` | The 4 GB live database | **No** (gitignored) |

## Why the database is NOT in git

The Stash SQLite database is ~4 GB. Git stores every version of a binary file in full, so 10 weekly backups would balloon the repo to 40+ GB. GitHub free also rejects files over 100 MB and Git LFS free storage is only 1 GB.

The database is backed up separately via `scripts/Backup-StashDatabase.ps1`, which compresses it and copies to the NAS.

## Metadata export strategy

The full Stash export (`D:\Stash\metadata\`) is several GB across 2M+ files. Most of it is regenerable. Only the **curated metadata** (manually edited data that can't be re-created by scanning) belongs in git.

### What is curated vs regenerable

| Data | Location | Curated? | In git? |
|---|---|---|---|
| Scene metadata (title, performers, tags, studio, URLs, details, stash_ids) | `exports/scenes/` | **Yes** | Yes (covers stripped) |
| Performer metadata (name, gender, body stats, stash_ids) | `exports/performers.json` | **Yes** | Yes |
| Studio metadata (name, URLs, stash_ids) | `exports/studios.json` | **Yes** | Yes |
| Tag definitions | `exports/tags.json` | **Yes** | Yes |
| Scene cover images (base64 in scene JSONs) | Stripped | No - re-extracted during scan | No |
| File technical metadata (codec, duration, fingerprints) | `D:\Stash\metadata\files\` | No - regenerated by scanning | No |
| Image file paths and gallery associations | `D:\Stash\metadata\images\` | No - regenerated by scanning | No |

### Cover image stripping

Each scene JSON from Stash's export contains a `cover` field with a base64-encoded image (~170 KB per scene). This is **98.7% of each file** and is regenerable during scanning. The `Sync-StashMetadataExport.ps1` script strips this field, reducing 15,234 scenes from **2.5 GB to 10 MB**.

### Export workflow

```powershell
# 1. Trigger Stash's full export (writes to D:\Stash\metadata\)
.\scripts\Invoke-StashMetadataExport.ps1

# 2. Sync curated metadata to the repo (strips covers from scenes)
.\scripts\Sync-StashMetadataExport.ps1 -CuratedDirs @("scenes")

# 3. Fetch performers/studios/tags via GraphQL (faster than full export)
.\scripts\Export-StashSummary.ps1

# 4. Commit
git add exports/
git commit -m "Update Stash metadata export"
```

## Backup the database

```powershell
# One-off backup
.\scripts\Backup-StashDatabase.ps1

# Or schedule it (see script header for Scheduled Task setup)
```

The script:
1. Calls Stash's GraphQL `backupDatabase` mutation (uses SQLite's online backup API - safe on a live DB)
2. Compresses the backup with 7-Zip (4 GB -> ~1-1.5 GB)
3. Copies the `.7z` to the NAS backup directory
4. Cleans up the uncompressed backup file
